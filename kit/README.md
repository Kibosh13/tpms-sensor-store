# Перенос ProДатчики в Яндекс KIT

Статус: исправленное оформление опубликовано на https://prodat4iki.ru/ после согласования владельцем предпросмотра 125. Активная версия — **127: 42 страницы, 141 секция**. Главная, каталог, услуги, контакты, доставка, оплата, подбор и корзина /cart отвечают HTTP 200. Все 19 основных CSS/JS-ресурсов главной проверены без ошибок. Тестовое добавление и удаление одного товара в корзине проверены без оформления заказа. Это публикация витрины, не подтверждение готовности оплаты и правовых документов к продажам.

15 октября исправлен визуальный перенос: восстановлены размеры, жирность заголовков (KIT сбрасывал часть в 400), единая сетка услуг с иконками и CTA, двухколоночная доставка, общая карточка контактов и оформление реальной товарной полки. Увеличен логотип штатной шапки. Товарные записи, цены и заказы не изменялись. Перед публикацией владелец просмотрел результат и явно подтвердил версию 125. Непубличные репетиции 121/123/125 не меняли оформление витрины: API-сверка подтвердила сохранение страниц и глобальных настроек прежней 120 в активной копии 126. После публикации API подтвердил активную 127.

`templates.mjs` и `brand.css` задают разметку, адаптивные стили и поля редактирования для клиента. `shelf.html`, `shelf.css`, `shelf.schema.json` — сохранённая и адаптированная товарная полка со штатными контроллерами KIT. `node kit/build.mjs` собирает HTML/CSS/JSON Schema и настройки в `generated/style-v2/`. Готовые тройки проверяются официальным `kit-custom-sections` перед загрузкой через `kit-storefront-constructor`. Хардкод фирменной палитры намеренно повторяет согласованный эталон; CSS ограничен секцией, без глобальных переопределений.

`style-refresh.json` хранит ID старых, новых и промежуточных шаблонов, номера предложения и действующей версии. `apply-style-refresh.mjs` — завершённая одноразовая миграция: подготавливала свежий workspace через официальный CLI, проверяла сохранность заполненных полей и не публиковала. После публикации повторный запуск заблокирован, чтобы не затереть будущие правки клиента. Проверки: `node --test kit/styles.test.mjs kit/picker.test.mjs kit/fitment-parser.test.mjs`. Публичные услуги, контакты и каталог проверены на ширине 375 px: горизонтального переполнения нет; цены полки видны целиком. Шапка/корзина остаются штатными компонентами KIT; полноценная форма подбора по-прежнему открывается в отдельном модуле, не имитируется неработающими select-полями на первом экране.

Клиент редактирует заголовки, описания, цены услуг, ссылки и контакты в стандартной панели KIT. Ширина контейнера, сетка и мобильные переходы остаются в шаблоне. Для фактов, услуг и доставки используются фиксированные поля, а не добавляемые списки. Схема содержит рекомендации по длине текстов; проверка показала, что KIT не ставит HTML-ограничение maxlength на обычные поля. Нельзя обещать строгий лимит ввода. Ручное изменение кода, шрифтов или структуры может изменить макет; обычные правки делаются через поля секции.

Для товаров используются реальные карточки, цены, фотографии и остатки KIT. Демонстрационный массив товаров GitHub Pages не должен заменять ассортимент магазина. После подключения API нужно прочитать текущую витрину, сохранить исходную версию вне репозитория, настроить тему/шапку/подвал и товарные секции по схеме конкретного магазина, создать самостоятельные страницы, подготовить непубличную proposal-версию и проверить её.

`patterns/*.answers.json` — параметры официальных товарных паттернов KIT. Карточка и полка главной используют штатные контроллеры KIT. Для полного каталога и поиска выбран нативный ProductsListing: сетка 3×6, 18 товаров на странице, сортировка и пагинация; образец кастомного листинга с тремя товарами не используется в рабочей витрине. `native-catalog.mjs` готовит замену только миграционных секций листинга. `normalize-layout.mjs` проверяет порядок: основной товар/поиск раньше рекомендаций, подвал последним. В редакторе KIT chrome может визуально сортироваться иначе, чем на рабочем сайте, поэтому обязательна проверка опубликованного результата.

Нативный фильтр по маркам требует характеристики «Марка авто». Из 4 924 опубликованных позиций она заполнена у 451; в выбранных категориях датчиков UI не предлагает её как фильтр. Массовое изменение товарных характеристик не выполнялось. `prepare-brand-backfill.mjs` готовит только предложения заполнения из явных строк применяемости, сохраняет существующие значения и не делает запросов записи. Перед будущим применением нужен свежий read-before-write каждого товара: PATCH массива характеристик в KIT заменяет весь массив, поэтому нельзя отправлять старый снимок поверх правок владельца.

API-токен хранится вне проекта в защищённом хранилище официального инструмента. Токены и полные выгрузки витрины не коммитятся.

KIT не исполняет пользовательские `<script>` и не поддерживает `iframe` в кастомных секциях. Страница /selection и меню подключены к отдельному модулю https://kibosh13.github.io/tpms-sensor-store/kit-selection.html. Владелец согласовал эту схему при публикации. Корзина, цены и оформление остаются в KIT; для единого домена модуля потребуется отдельное согласованное размещение и DNS.

## Интерактивный модуль

`site/kit-selection.html` использует реальные опубликованные товары KIT. Справочник собран из полного чтения 4 924 опубликованных позиций: распознаваемая применяемость найдена у 4 439 товаров. Это данные из описаний продавца, не профессиональная VIN/OE-матрица. Условия по VIN/кузову показываются явно. Кандидаты не выдаются за гарантированно совместимые датчики.

Модуль не сохраняет VIN. Собственная матрица по автомобилю содержит 75 марок и 38 996 строк применяемости, автоматически извлечённых из описаний продавца. Это не 75 марок с полной локальной VIN-расшифровкой: локальная точная VIN-база пока содержит только Mercedes-Benz 210.026 (E 320 CDI / W210). Пример Mercedes из брифа определяется локально без vPIC; точный год не вычисляется по 10-му символу европейского VIN. Публичные тесты используют синтетический серийный номер. Если локальной записи нет, vPIC служит дополнительным источником, а неполные данные требуют уточнения. Неизвестный тип TPMS, год или неоднозначная модель блокируют подтверждённую выдачу по VIN.

Профессионального источника у владельца нет, поэтому развитие системы — собственная проверенная база: коды моделей, рынок, период выпуска, OE-номер, протокол и ограничения по комплектации. Для нового VIN-правила нужна запись производителя, а для подтверждённого датчика — проверенная связь с конкретной комплектацией. Нельзя выводить наличие прямой TPMS из одного WMI или автоматически считать все датчики нужной частоты совместимыми. Полный автоматический подбор комплектации по произвольному VIN пока **не реализован**; никаких обещаний полной мировой VIN/OE-базы нет.

Начальная загрузка содержит марки, модели и годы; товары загружаются отдельно по выбранной марке. В публичных файлах нет цен-снимков, точных складских количеств, резервов или токена. Цена и покупка — в KIT. Данные применяемости и доступность в модуле являются снимком на дату экспорта, поэтому после изменения товаров требуется обновление:

1. Официальным `yandex-kit-cabinet` получить полную выгрузку опубликованных товаров **вне репозитория**.
2. Запустить `node kit/build-picker.mjs /absolute/path/published-products.json`.
3. Запустить `node kit/fitment-parser.test.mjs` и `node kit/picker.test.mjs`.
4. Отправить изменённые файлы в main и gh-pages. Сортировка и отдельные файлы марок сохраняют небольшие последующие diff.

## До коммерческого запуска

- В KIT пока не подключены Яндекс Пэй и онлайн-касса; подтверждение реквизитов и соглашения выполняет владелец. Агент не подписывает документы и не делает платёжные тестовые покупки.
- Часть карточек Autel указывает гарантию 1 год, бриф — 2 года. Товарные данные не переписаны; нужно согласование владельца.
- Правовые страницы исходного KIT содержат шаблонные тексты. Их нужно подготовить и утвердить владельцу до приёма реальных заказов.
- Оформление уже опубликовано. Не запускать `apply-layout.mjs` поверх готового магазина с правками клиента: это подготовительный миграционный инструмент. Последующие правки — через свежий content pull и минимальные операции страницы/секции.
- API-токен попал в разговор по инициативе пользователя; после работы его нужно отозвать. Секрет находится вне проекта, а не в GitHub.
